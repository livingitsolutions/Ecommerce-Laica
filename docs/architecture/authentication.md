# Customer identity: staged, not activated

Supabase Auth is the selected identity provider only. Netlify PostgreSQL is the authority for application identities, account suspension, customer records, platform authority and seller memberships. The browser must never talk directly to a privileged provider service or submit a trusted role. No provider SDK, account issuer, runtime adapter or production auth endpoint is installed. The server-neutral contract in `server/identity` runs with injected ports in isolated tests; the site cannot activate it by setting a flag.

## Session contract for the future adapter

1. A server-only provider client uses a pinned HTTPS project and supported email/password APIs. Validate the subject, exact issuer, expected audience, expiry and verified email before provisioning. Never link by email or provider user metadata. Verify a callback's purpose and consume it once. Provision using the parameterized query in `db/identity.ts`; zero rows means deny, not retry with another issuer. Only provision after proof, never on an unconfirmed signup. Provisioning and its audit event must commit together.
2. Store only an opaque random reference in the host-only cookie, not a role, subject, password or provider JWT. The reference identifies server-side state; it is not a custom identity token. Before activation, implement a Netlify PostgreSQL session vault: store only a digest of the reference, user FK, purpose, issuance/absolute expiry, revocation state and authenticated-encrypted provider tokens with key version. Commit no provider material to the browser, URLs, storage, logs or audit data. There is no vault or token encryption implementation yet.
3. Each resolution revalidates provider identity, session revocation, account status and email verification; load current membership from the database on every protected operation. `HttpOnly; Secure; SameSite=Lax; Path=/`, `__Host-` prefix, no Domain, and eight-hour absolute maximum. Also enforce absolute expiry in the vault, including after refresh. Rotate the reference after login and recovery; do not adopt a presented reference at login. Implement idle expiry and a shorter recovery lifetime before activation.
4. When access expires, lock the session row, recheck state, refresh once and atomically replace the encrypted pair. An ambiguous provider/DB failure invalidates the local session and forces login; never race refresh attempts or extend absolute expiry. The contract rejects a change of subject, reference or purpose during refresh. The adapter must not treat local cookie destruction as provider logout. Revoke locally first, then revoke the provider session with retries; existing access JWTs can outlive provider sign-out. Password reset consumes a recovery-only session once and invalidates all local sessions; a normal login cannot reset through this endpoint.
5. No CORS grants. All mutations, including pre-login, require exact configured Origin, JSON and a custom request header; reject preflights and cross-origin credentials. Set no-store on every API response and exclude these routes from CDN/service-worker caching. Trusted peer and seller scope come from runtime/deployment context, never forwarding headers chosen by the browser.

## Portable API contract (not routed)

All paths below are relative to `/api/identity/`. Content is JSON. Unknown routes/methods have no default handler granting access. Do not ship a catch-all SPA rewrite ahead of a future API route. No impersonation, role-assignment, owner bootstrap or onboarding API exists.

| Method and path                   | Scope and result                                                                                                                                                                                            |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST `register`, `recover`        | Anonymous, generic 202 on eligible/ineligible delivery; signup also requires a separate gate. Adapter must normalize provider duplicate and unknown-email results without exposing timing or account state. |
| POST `login`, `confirm`           | Valid verified principal; establish an account or a restricted recovery cookie. `confirm` accepts a POSTed single-use proof with explicit purpose, not a GET mutation.                                      |
| POST `logout`, `reset`            | Revoke session and expire cookie; reset additionally requires recovery purpose and a valid new password.                                                                                                    |
| GET `session`, `verification`     | Verified active account only; no tokens or PII returned.                                                                                                                                                    |
| GET/PATCH `profile`               | Current customer only. Strict display-name input.                                                                                                                                                           |
| GET/POST `addresses`              | List/add within verified customer and configured storefront only. No arbitrary resource ID or seller selector.                                                                                              |
| GET `memberships`, `seller-admin` | Current active memberships; workspace requires membership for the trusted seller. No product/order/live management handlers.                                                                                |

Use a durable per-peer limit for every operation plus an independent, normalized account bucket for email flows. Key buckets by HMAC of dimension, action and identifier; do not store email/IP in counters. `consumeLimit` is an atomic, fixed-window SQL primitive; zero returned rows denies. A runtime adapter, threshold policy, bounded expired-bucket cleanup and provider throttling are still required. Return generic errors and generated correlation IDs; redact bodies, cookies, proofs, addresses and authorization headers in all instrumentation. Audit outages deny access. Protected writes and their audit must share a database transaction, not rely solely on the boundary's request outcome event.
