# Sprint 0 architecture

The Bag Gallery is an initial brand on a category-neutral commerce foundation. React 19, Vite, strict TypeScript, Tailwind CSS v4, and Zod form a client-rendered demonstration. PHP prices use integer minor units. No API, customer identity, upload, checkout, stream, or persistent cart is activated. Static fictional fixtures are examples, never a production source of truth.

Feature boundaries live under `src/features`: storefront presentation, catalog, categories, inventory, cart, orders, payments, live-selling, media, identity, and admin. Implemented components belong to catalog, media, cart, and live-selling; other modules contain boundary documents rather than pretend workflows. `src/shared` owns accessible modal infrastructure and `db` owns the dormant schema. The initial application shell composes navigation and storefront sections; catalog logic has no brand dependency.

Deployment target: Netlify static `dist` output with SPA routing. The official current guidance recommends a Netlify Server for new request-driven APIs, and Netlify Functions for scheduled expiry, long media processing, and platform events. This differs from a Functions-only API interpretation of the requested stack. No server is needed or deployed in Sprint 0; confirm the API runtime decision before Sprint 1. A future Server requires Node 24 and an `/api/*` route boundary ahead of SPA fallback. Do not silently move a future API behind the existing catch-all rewrite.

Runtime flow for Sprint 1: browser → validated/authenticated Netlify API → seller-scoped service → Drizzle → Netlify Database. A checkout service owns inventory, order and payment orchestration; providers are adapters. No application module may reach a payment provider directly from the browser. Object storage is Netlify Blobs, not PostgreSQL binaries. See the other architecture documents for review gates.

Admin plan: dashboard aggregates, product/category/dynamic attribute editing, option matrix, quarantined media workflow, stock adjustment ledger, order processing, payment reconciliation, live session moderation, support, storefront settings, promotions and analytics. Gate each capability by seller membership and audit all mutations. Promotions need future pricing/usage tables; analytics need consent, event definitions and retention. Full workflows and seller onboarding/commissions/payouts are outside Sprint 0.
