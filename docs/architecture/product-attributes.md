# Configurable category attributes

category_attributes stores a seller-owned category key, label, type (text, numeric, boolean, select), required flag, unit and filterable flag. category_attribute_options stores stable selectable IDs and labels. product_attribute_values stores one typed value per product/attribute with an exactly-one-value check. Select values reference an option belonging to that attribute and seller. Examples: material (text), capacity (numeric with L), water-resistant (boolean), and device connector (select). None is a required global column.

Before persistence, Zod discriminated unions must be built from server-loaded definitions, with length/range/allowed-option validation. Never trust an attribute type sent by a client. The design needs an activation migration trigger or transactional service check that enforces the value's column matches the definition type, category applicability and inherited required attributes. These cross-table rules are documented requirements, not implemented protections. Category cycles beyond self-parenting need a recursive cycle guard before activation; self-parenting is already constrained in the proposal.

Product-specific specifications are optional typed definitions assigned through a category (including a general specifications category), rather than an unbounded product JSON dumping ground. The fixture UI uses a Record projection for rendering only. Future per-product attribute definitions should extend the definition layer with explicit ownership and applicability, not add product-type columns. Inheritance resolves root-to-leaf with stable definition IDs; conflicting keys are rejected on category assignment. Attribute removal and type changes require usage checks, versioned conversion and audit logs. Required checks happen when publishing, allowing incomplete drafts.
