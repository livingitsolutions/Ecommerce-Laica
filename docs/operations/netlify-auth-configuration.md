# Server configuration and activation

No variables activate this revision. The port-based boundary accepts only an isolated-test context and a reserved origin; no HTTP entry point imports it. The UI neither fetches identity APIs nor collects credentials. Keep the conventional Functions requirement; no Netlify Server substitute was authorized. First obtain an environment that permits the approved Functions runtime and Supabase-only integration.

Proposed server-only inputs (never use a `VITE_` prefix): `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `AUTH_ORIGIN` (exact canonical HTTPS origin), `AUTH_COOKIE_SECRET` (versioned key material for a future session vault, with separate derived encryption and bucket keys), `AUTH_ENABLED`, and `PUBLIC_REGISTRATION_ENABLED`. Use the managed Netlify Database binding for application data, not Supabase and not a client-supplied DSN. Provide trusted storefront-to-seller mapping. Secrets must be isolated by environment, rotated and kept out of logs. No bootstrap or seller onboarding runtime flags are supported.

Release sequence: (1) reconcile migration ledger, rehearse recovery and approve SQL; (2) implement the provider, runtime, scoped repositories, session vault and durable rate/audit adapters; (3) run security, CSP, accessibility, revoke/refresh race and multi-tenant tests in isolation; (4) verify API precedence over the SPA, no-store on all errors, safe logging, SMTP sandbox and deny-by-default startup; (5) obtain separate production migration and deployment approvals, with registration still off; (6) use approved controlled smoke identities only; (7) obtain separate approval for public registration on both provider and server. A readiness probe must verify the pinned provider, DB schema version, restricted grants, vault keys and rate/audit availability, not merely test that flags exist.

Emergency shutdown: close provider signup and registration gate first, disable identity routes, revoke local sessions and provider refresh tokens, retain audit evidence. Leave public catalog routes intact. Reverting static code does not revoke tokens, reverse migrations or recall email. Never copy production secrets into previews or enable test adapters from request parameters.
