# Supabase Auth release prerequisites

Design only. No provider project is connected. Keep email signups disabled at Supabase **and** in the server until launch approval: disabling the storefront alone does not prevent direct provider signups. Do not activate another identity service as a substitute.

Use separate nonproduction and production projects. Pin the project URL and issuer; enable email confirmation, disable anonymous signup and unused providers, configure minimum password quality and authentication throttles. Use a server-only client with session persistence, automatic refresh and URL detection disabled. Select only Auth APIs: `signUp`, `signInWithPassword`, `verifyOtp`, `getUser`, `refreshSession`, `signOut`, `resetPasswordForEmail` and `updateUser`. Never call commerce tables in Supabase. Do not use the service-role key for ordinary authentication.

Set the canonical HTTPS Site URL. Allowlist only an exact purpose-built landing URL per trusted origin (planned production: `https://dapper-squirrel-8939f0.netlify.app/account/confirm`); never wildcard previews or accept a user-supplied next URL. This landing page is **not implemented**. Configure templates for purpose-bound single-use verification and recovery proofs. Prefer a manually entered OTP; do not send access/refresh tokens to a browser URL. If using a token hash link, prohibit external resources and referrers on the landing page, redact query logs, remove proof from history, and require deliberate POST confirmation so mail scanners cannot consume it on GET. Do not allow implicit session redirects to the static Vite app.

Configure an approved SMTP sender and delivery domain, confirmation/recovery templates, expiry and rate limits. Provider email defaults are not evidence of deliverability. Test signup, duplicate signup, replay, expired proofs, reset and session revocation using a separate provider project and capture-only mailbox. Validate provider anti-enumeration behavior including timing and direct Auth API exposure. Require MFA and an approved recovery process for privileged operators before granting authority. Never send test messages to customers.
